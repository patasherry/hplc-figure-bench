# Instructions for coding agents

This file is the shared rulebook for every coding agent working on this repository, including Google Jules and Claude Code. `CLAUDE.md` points here, so there is one source of truth. If you change how the project works, update this file in the same pull request.

## What this project is

Protein Purification Bench is a single-file HTML application for making publication-quality protein purification figures: HPLC and ÄKTA chromatograms, SDS-PAGE gels with densitometry, SEC calibration, NanoDrop readings, and a step-by-step purification workflow figure with a written summary and methods text.

The owner is a biochemistry graduate student who uses it for real lab data. Scientific correctness matters more than new features.

## Repository layout

- `hplc-figure-bench(WF1.13).html`: the entire application (HTML, CSS and JavaScript in one file). Do not rename it unless the task asks you to. The owner manages the version label.

**The name.** The app is called **Protein Purification Bench** (the Direction board's unanimous choice on #222, 2026-10-30, carried out in PR #1018). That is the name in the page title, the header and all prose. Three things keep the old name for good, because they are data rather than labels: the file name above, the `hplc-fig-opt` settings key, and the `app: 'HPLC Figure Bench'` field in project files, which both the exporter writes and the importer checks. Renaming any of those stops every project saved before the rename from loading, and stops every file saved after it from opening in an older copy. `tests/suites/01_name.js` checks both halves.
- `README.md`: user-facing documentation.
- `AGENTS.md`: this file.
- `CLAUDE.md`: points Claude Code to this file.
- `.github/workflows/`: GitHub Actions: Claude Code (automatic PR review on app changes, `@claude` mentions) and the test suite on every PR.
- `.github/copilot-instructions.md` and `.github/workflows/copilot-setup-steps.yml`: standing instructions for GitHub Copilot (coding agent and code review), and the setup of its workspace so it can run the tests.
- `tests/`: the automated browser test suite and its synthetic test data.

## How the code is organized

Read docs/CODEMAP.md first. Open only the lines you need from the HTML file. Before writing any browser test or inspection script, read docs/AGENT_TIPS.md: it lists the traps that stall agents (hidden controls, the home-screen-only new-project box, figure tabs hidden inside projects) and the harness helpers to use instead.

- One `<style>` block, then one `<script>` block.
- All JavaScript lives inside a single strict-mode IIFE: `(function(){ "use strict"; ... })();`. There are no modules, no build step, no package manager and no framework. Keep it that way.
- The script is divided into sections marked with comments like `/* ---------- peak integration ---------- */`. Search for these markers to find code. Put new code in the section it belongs to, and add a new marker only for a genuinely new area.
- Main sections, in order: helpers, parsing (generic, ÄKTA/UNICORN, UNICORN 7 .zip), traces and runs, peak integration, size exclusion (SEC), figures (HPLC overlay, ÄKTA run chart), gels (auto crop, densitometry, band tags and purity), composite workflow figure, upstream steps (construct, expression, lysis, GenBank), run conditions, UI, loading, protein (sequence properties, PDB), NanoDrop, SEC panel, projects, home, step timeline, quick fill, export, example data.

### Settings

- All user settings live in the `opt` object. Defaults are in `DEF` near the top of the script.
- `opt` is saved to `localStorage` under the key `hplc-fig-opt` by `saveOpt()`.
- To add a setting, add its default to `DEF`. Older saved settings are merged over `DEF`, so new keys get their defaults automatically.
- To change an existing default for people who already have saved settings, use a one-time migration flag in the style of the existing `tidy13` and `tidy14` flags. Never silently reinterpret an existing key.

### Projects and storage

`storeInit()` picks one of three storage modes:

- `cloud`: when the page is hosted somewhere that provides `window.claude.use('db' | 'user' | 'assets')`.
- `local`: IndexedDB database `hfb-projects`, object store `projects`.
- `none`: no storage available.

Projects can also be exported and imported as a single JSON file.

**Backward compatibility is required.** Saved settings, IndexedDB projects and exported project JSON files from earlier versions must keep loading. If a data format must change, write code that upgrades the old format when it is read.

### Network dependencies

The app loads only these external resources. Do not add new ones without saying so clearly in the PR description.

- Google Fonts (`fonts.googleapis.com`, `fonts.gstatic.com`) for Instrument Sans.
- `pako` 2.1.0 from cdnjs and `UTIF` 3.1.0 from jsDelivr, loaded on demand to read TIFF gel images.
- RCSB PDB (`files.rcsb.org/download/`) when the user requests a PDB structure.

## Scientific values

Do not change scientific constants without a cited source in the PR description. These include protein ladder sizes (`LADDERS`), known contaminant masses (`KNOWN_DEFAULT`), extinction coefficient and molecular weight calculations, SEC calibration math, and peak integration methods.

Figure defaults follow publication conventions: the Okabe-Ito colorblind-safe palette, Arial, 600 dpi, and journal column widths in `PRESETS`. Keep them unless the task says otherwise.

## Testing

`tests/` holds an automated browser test suite (Playwright, headless Chromium, including `25_gels.js`). See `tests/README.md` for details.

**Before opening a PR that changes the HTML file:**

1. Run the suite on your change and on `main`, and compare them:
   ```
   cd tests
   node compare.js
   ```
   This tests your working copy of the app against the version on `origin/main` (read from git) and writes `tests/results/compare.md`. A full run takes several minutes. If you cannot run the comparison, run `node run.js` on your change at least.
2. Paste the summary into the PR description: pass and fail counts per suite, and every regression (a check that passed on `main` and fails on your branch).
3. A regression is either fixed, or explained in the PR as intended.
4. When you fix a bug or add a feature, add a check for it to the suite it belongs to.
5. A new suite is a file `tests/suites/NN_name.js`. The Test suite workflow finds it by its file name, so do not edit `.github/workflows/tests.yml` to add it.

The `Test suite` GitHub Action also runs this comparison on every PR that touches the app or the tests, and posts a results table on every PR. A PR with regressions shows a failed check. Running it yourself first is still expected, so problems are found before the PR is opened.

Checks that already fail on `main` are known problems. They are not yours to fix unless the task asks.

After running tests, read the output of node failures.js, not the full logs.

**Rules for the suite:**

- Tests drive the app only through its UI and DOM, never internal functions.
- All test data is synthetic. Never add real lab files to `tests/`. Inputs that were first real files are mapped to synthetic stand-ins in `tests/lib/harness.js`.
- Do not weaken or delete a check to make a change pass. If a check is wrong, say why in the PR.
- User-visible numerical fixes require minimal main-failing evidence: add one UI-level synthetic case that fails on main and passes on the branch. Assert the displayed value with an appropriate tolerance or exact text when rounding is contractual, allowing domain-specific tests to define the expected semantics.

For a quick manual look: open the HTML file in a browser (example chromatograms load automatically), or add `#quick` to the URL for Quick-Figure mode. `#selftest` exposes internal functions on `window.__HFB` for the browser console.

In every PR description, say exactly what you tested and how. Do not claim testing that did not happen.

## Rules for pull requests

1. **One task per PR.** Keep changes as small as the task allows.
2. **Never reformat or reindent the file.** The HTML file is very large, and a formatting change produces an unreadable diff that hides real changes. Match the surrounding code style, which is compact.
3. **Do not add dependencies, frameworks or build tools.**
4. **Update `README.md`** when user-visible behavior, supported formats, exports or network dependencies change.
5. **Never commit real lab data** (chromatograms, gel images, sequences). The owner's results may be unpublished.
6. **Explain the change** in the PR description: what changed, why, how it was tested, and anything uncertain.
7. Do not merge. The local manager merges PRs that pass the Test suite and the review gate and do not change a reported number (the owner's choice, `auto_merge`). Changes to reported numbers, after the owner's OK (or the board's strong consensus), are reviewed by the AI lead reviewer the owner picks (see **AI lead review**), and by the coordinator (Claude) when he picks Claude or the reviewer is unsure.

## How agents divide the work

`docs/GOALS.md` is the owner's list of priorities. Every agent weighs its work by it. Once a day the lead posts a **Lead check-in** on issue #17, and the local manager follows the newest one.

Jules' questions go up a ladder, run by the local manager on the owner's PC: the local model tries three times (quick, then twice more with the code in front of it, each answer checked by a second local pass), then Gemini (given the code it needs), then ChatGPT (Codex, read-only), then the local model once more with their notes, then Claude Code (read-only), and only then the lead (`for-coordinator`). Each answer says who decided and the path it took. Anything that would change a reported number goes to the owner (`needs-owner`) instead. The owner answers on the issue with a comment starting **OK** (the manager labels it `owner-approved` and queues it) or **No** (`owner-declined`, taken out of the queue). Merging app changes stays with the lead, and a `needs-owner` change is merged only with `owner-approved`.

**Empty pull requests are never merged.** A PR that changes no files passes every file and test check vacuously, so until Nov 5 such PRs were auto-merged and closed their issues ("Fixes #N") while the bug stayed in the app: #770 and half of #772 were lost that way, among 12 empty merges. The manager's gate now closes an empty PR and puts its issue back in `jules-queue`, and the Jules leader flags one for the coordinator instead of merging. That check runs **before** the gate waits for the Test suite, because an empty PR touches neither the app nor `tests/`, so the suite never runs on it and the wait never ends: #1016, #1058, #1076, #1080 and #1081 sat open for up to a day that way, each with a commit message claiming a fix and nothing in the commit. Zero files needs no test run to judge. If a fix really is already on main, say so on the issue and close the issue directly, without a PR.

**Automatic review gate.** When the Test suite finishes on a PR that changes the app, the local manager checks it with plain code: only the app, `tests/`, `docs/` and `README.md` change; no regressions; at least one check fails on main and passes on the PR ("Checks this PR fixes"); no check it adds fails on the PR; no existing check is deleted or commented out; no test reaches into `window.__HFB`; `expected.json` is not rewritten; no merge conflict. A PR that fails is closed, the reasons are added to its issue, and the issue goes back to `jules-queue` (at most twice, then `for-coordinator`). A PR that passes and doesn't change a reported number (its issue has neither `needs-owner` nor `owner-approved`) is **merged by the manager**, one per pass. One that changes a number gets `ready-for-lead` for the lead's review, plus `needs-owner` if the owner's OK is still missing.

The gate also checks PRs that only change tests or docs when they carry stray files. When the only problems are stray files (scratch scripts, logs) or a merge conflict, the manager **rebuilds the PR itself**: it applies just the PR's own app and test changes on the current main as a new PR on `claude/issue-N`, closes the original, and the new PR goes through the tests and the gate. No Jules retry is spent on that. The same rebuild covers two cases where GitHub never runs the tests: a PR that conflicts with main for 30 minutes with no test run, and a finished Copilot cloud-agent PR (a draft that asks the owner for review), whose tests GitHub holds for a person to approve. The rebuild carries only the app, `tests/`, `docs/` and `README.md`, so workflow changes never run unreviewed.

**Claude Code jobs.** When Jules and then Copilot are out of tries (the gate sent Jules back twice, or 3 Jules sessions failed, and Copilot's attempt failed too), the issue gets `for-claude-code`. The local manager runs Claude Code on the owner's PC in a separate git worktree (`~/hfb-work/issue-N`, from `origin/main`), limited to editing files and running the test suites. Each job's worktree gets a link to the main checkout's `tests/node_modules` (a junction on Windows, never committed, removed before the worktree is deleted) so the agent can run the suites before the PR opens. The same holds for Copilot CLI jobs. The manager checks that only the app and `tests/` changed, commits, pushes the branch `claude/issue-N` (with `copilot/issue-N` for Copilot CLI jobs and `antigravity/issue-N` for Antigravity jobs `openclaw/issue-N` for OpenClaw jobs and `codex/issue-N` for Codex jobs, the only branches it ever pushes) and opens the PR. That PR goes through the Test suite and the gate like any other, and if it fails it goes to the lead. At most 3 jobs a day (`max_claude_jobs`). Claude Code (read-only) is also the last step of the question ladder before the lead.

**GitHub Copilot coding agent (off by default).** Patrick has no Copilot credits, so `copilot_mode` is `off`: no job goes to Copilot, a job whose turn would be Copilot's (`for-copilot`) goes straight to Claude Code, and the Copilot CLI is not used. Setting `copilot_mode` to `auto`, `cloud` or `cli` in the settings file restores what follows. A second coding worker beside Jules, started by the local manager with the owner's token (the API takes only user tokens, so the leader can't). Whenever a job waits for Jules (`copilot_when_queue`, 1), the manager assigns the newest one (not `needs-owner` or `from-patrick`) to `copilot-swe-agent[bot]`, with the AGENTS.md rules as custom instructions: at most 4 at a time (`copilot_at_once`) and 10 a day (`max_copilot_jobs`). Copilot also gets the **next try when Jules is out of tries** (`for-copilot`), before Claude Code. The issue gets `copilot-running`, then `copilot-done` when Copilot's PR ("Closes #N") appears. Copilot's PRs go through the Test suite and the gate like any other. One that fails, or a retry with no PR after 8 hours, goes to Claude Code (`for-claude-code`). An ordinary job with no PR after 8 hours goes back to `jules-queue`. It needs a paid Copilot plan (the owner has it through GitHub Education). After a refusal the manager backs off for 6 hours, or until it restarts, and sends retries straight to Claude Code. When Copilot takes a job but posts that it is unable to start (for example out of GitHub AI Credits), the manager hands the job back at once (to Jules, or to Claude Code for a retry) and pauses Copilot for 24 hours, also across restarts. While the cloud agent is paused, the manager runs the **Copilot CLI** on the owner's PC instead (`copilot_mode`, `auto` by default; `cloud` or `cli` to use only one): one job at a time in its own worktree (`~/hfb-work/copilot-N`), allowed to edit files and run only node, python and read-only git. The manager checks that only the app and `tests/` changed, commits, pushes `copilot/issue-N` and opens the PR, which the gate treats like the cloud agent's. It shares the Copilot daily cap.

**Google Antigravity agent.** A third coding worker, reached through the Gemini API (Interactions API, agent `antigravity-preview-09-2026`, the same `GEMINI_API_KEY`), so it runs from the PC manager and the cloud manager alike.

**Antigravity takes the app-changing work (Patrick's choice, 2026-11-05).** The Jules leader routes every `jules-queue` issue that is not light to `for-antigravity` instead of starting it, and Jules keeps the light ones. The routing is in the leader because the leader is what races: it checks every 3 minutes and used to start the job before the manager saw it, which is why the API route had produced no pull request at all by Nov 5 while the queue looked busy. `AG_TAKES_APP=0` in the leader's environment turns the split off.

Three things stop a job getting stuck on that label. A `for-antigravity` job nobody has started within `antigravity_stall_minutes` (45) goes to Jules, and so does every such job at once while the Gemini API is paused, which it is for 6 hours after a refusal. A job Antigravity fails goes back to it for one more try (`antigravity_max_tries`) and then to Jules. Either way it is labelled `ag-returned`, which stops the leader routing it to Antigravity again, so a job can never bounce between the two.

**The Antigravity CLI on the owner's PC (`agy`), the working route.** Patrick has Google AI Pro, and the Antigravity CLI is included at every subscription tier, drawing on the subscription quota through the sign-in an interactive `agy` session caches, not on the Gemini API key whose project has refused every Interactions call. It runs headless, so the manager treats it like Codex and OpenClaw: one job at a time in its own worktree (`~/hfb-work/agy-N`), `agy -p` with `--output-format text`, `--print-timeout`, `--model` and `--dangerously-skip-permissions` (see below), at most `max_agy_jobs` (8) a day, stopped after `agy_hours` (2). It runs on **3.8 Flash** (`agy_model`, default `gemini-3.8-flash`), Patrick's choice over the Gemini 4 Argon the sign-in defaults to, to spend less of the AI Pro quota per job. `--model` is the only headless way to pick one, since `/model` is interactive; `agy models` lists the names a build accepts, and `agy_model: ""` drops the flag and takes the sign-in's default. The manager logs the model when a job starts, so a name this build rejects shows up as that and not as a mystery failure. **Its queue is `for-antigravity`**, the same label the Jules leader fills, so the CLI serves the app-changing split whether or not the API ever works. It pushes `agy/issue-N`, and the gate treats its PRs like Copilot's. Needs the CLI findable and one interactive sign-in first; `agy_jobs_on: false` turns it off. `agy_exe` names its full path when PATH does not have it, which on Windows is easy to hit, since it is a shim (`agy.cmd`) and a manager started from a shell whose PATH predates the install will not see it. `have_agy()` also treats a start that actually worked as proof for 7 days: on 2026-11-05 the CLI opened #1070 at 21:26 and two hours later the stall guard swept six jobs to Jules saying it was not installed, so a missed PATH lookup must never read as "not installed" again. The reason a sweep gives is now the real one, naming PATH, the off switch or the cloud copy.

**It runs with permission prompts skipped, because on Windows nothing else works.** In headless mode an approval nobody can answer is *soft-denied*: the run continues, exits 0 and has changed no files, which the runner then reports as "no changes". On Windows the CLI still uses the older permission system, and `permissions.allow` rules in `~/.gemini/antigravity-cli/settings.json` do not reach it: on 2026-11-05 both `write_file(*)` and a concrete `write_file(/Users/Patrick)` were ignored and the smoke test auto-denied the write, while `--dangerously-skip-permissions` edited the file at the first try. So `agy_yolo` defaults to true. This is the least contained worker here, less than Codex's `workspace-write`: during a job the agent may run any command on the PC, not only writes inside the worktree. What limits it is that the job runs in a throwaway worktree (`~/hfb-work/agy-N`), the task file is the manager's own, and the manager checks which files changed before it pushes. `agy_sandbox` would add `--sandbox` for containment but is **off** by default: it is unverified on Windows, and an unsupported flag fails the same silent way the permissions did. Turn it on once a smoke test shows the CLI still edits a file with both flags.

Because the CLI takes one job at a time, a backlog on `for-antigravity` is not a stall: the stall guard keeps the newest `agy_backlog` (6) for it and gives Jules the rest, and sweeps the lot only when the API is paused *and* the CLI is not installed.

**The API route was refusing every call, and it was our own sandboxes.** Every attempt from Nov 1 to Nov 5 returned `HTTP 429 Too Many Requests` on the first call of the day with no usage behind it, which was read here as the agent having no quota on this key's tier. That was wrong. Once `gem_api` started reporting the response body, on Nov 6, the message turned out to be `Project environment storage quota exceeded`: every call asks for `environment: 'remote'`, which creates a sandbox, and the API keeps each sandbox for **7 days** after its last activity whether or not anything needs it. At up to 40 jobs a day the project filled with our own leftovers. Nothing was wrong with the tier.

On a refusal naming the environment storage quota the manager sweeps and retries on the next pass, at most one sweep an hour, instead of counting a refusal. Any other refusal still counts (`antigravity_refusals_before_dead`, 3) and then backs off for `antigravity_dead_hours` (24) rather than retrying every 6 hours forever, and says so once on #17, now distinguishing the two causes. A call that succeeds clears the streak by itself. The desktop app and the `agy` CLI serve the queue either way.

It labels the issue `claude-cloud-running`, works on `claude/issue-N` from main, runs the suites it touched, opens the PR (`claude-cloud-done`), and sends a job it can't finish to `for-coordinator`. Its PRs go through the Test suite and the gate like any other. Label an issue `for-claude-cloud` to send it there on purpose.

**Usability tester (scheduled task, paused).** Paused on Oct 31 for the same reason; the usability scopes below do this job on the PC with the local model. When it is on, a Claude Code cloud session starts every 4 hours and uses the app the way a person would. It drives it with Playwright on the synthetic data, works through one journey per run, rotating through first visit, workflow, branches, gels, SEC, zoom and full view, phone width and dark mode, and projects, and looks at its screenshots. **Usability scopes (PC manager, local model).** Every 3 hours while the PC is on (`ux_every_hours`, 0 turns it off), the manager walks one test scope from `tests/ux/scopes.js` through the app with `node tests/ux/scope.js <scope> <folder>`. The scopes are use cases (first visit, workflow, layout and dragging, gels, SEC, zoom and full view, phone width and dark mode, projects), taken in turn. The runner uses synthetic data only, takes a screenshot after each step, and records with plain code what a user would hit: steps that could not be done, page errors, sideways scrolling, cut-off hints and labels, controls off the screen edge, and overlapping figure text. The local model then reads each screenshot as a first-time user and notes up to 3 problems (Ollama vision; skipped if the model can't take images). One screenshot gets `ux_vision_seconds` (180, down from 600: a timeout costs the pass that whole time and every duty behind it waits), and after `ux_vision_give_up` (2) **failed** calls in a row the walk finishes on plain checks alone. A screenshot the model read and found nothing wrong in is not a failure and never counts towards that, which is the common case. The report becomes a `ux-report` issue, one per scope, with later walks added as comments. It also becomes the Direction board's next topic: the advisers check which findings are real and propose fixes, adopted like any board proposal. The scope files are not a suite, so CI never runs them. Add a use case by adding a scope.

**AI lead review.** PRs that pass the gate but change a reported number (`ready-for-lead`, no regressions, and the issue `owner-approved` or `board-approved`) are reviewed by the AI the owner picks with a comment on #17 starting **Reviewer:** `gemini` (the default), `antigravity` or `claude`. Antigravity checks the PR out in its sandbox and can run the suites, in the background. The verdict is posted on the PR with the commit it covers:
- **merge:** the manager merges it, one per pass.
- **send_back:** the notes go on the issue, the PR is closed and the issue returns to `jules-queue`.
- **lead:** it gets `for-coordinator` for Claude.
With `Reviewer: claude` nothing is reviewed automatically and the lead handles them as before. If Antigravity is refused, the review falls back to Gemini.

**Claude Science inbox (#782).** Patrick posts findings from Claude Science's independent audits there, one per comment (or several, each under its own `# ` heading), pasted or attached as `.md` or `.txt` files. **Offline relay (`docs/RELAY.md`).** For questions an agent with no access to the repository can answer. Patrick labels an issue `needs-relay`; the manager (PC or cloud) posts a self-contained request block with a numbered excerpt of the app, and Patrick carries the agent's response block back as a comment. The manager posts a request only for a label Patrick added and files work only from a response Patrick pasted. Six checks run in order; the one that matters is that every hunk's old side is still verbatim in the app at current main, so a stale patch is refused and a fresh request is emitted (at most `relay_max_rounds`, 1). The aim is one round: the excerpt is picked by explicit range, then line number, then the functions the text names, then the phrases it quotes that appear verbatim in the app (a UI issue quotes its own button text), then the app sections whose subject matches its words (rare words count for more), capped at `relay_max_lines`; every request carries `tests/lib/harness.js` (a patch must bring a test, and without the harness an agent writes it against `@playwright/test`), and a job about checks gets a worked suite too; the response parser is deliberately loose about blank lines, fence style, tags, sha length (a `base` is compared by prefix, as git does) and **indentation**, since correct answers kept being thrown away: two on #1015, one for a blank line after `patch:` and one for echoing the full commit sha, and two on #1064, whose patch sat exactly at the lines its own header named and carried three spaces where the app has two. A hunk now matches on its content as a contiguous run of lines, ignoring each line's leading and trailing whitespace, since a filed patch is carried out by a coding agent and never fed to `git apply`; order and contiguity still hold, so an invented hunk is still caught. A hunk that matches only the app as it stood at the request's own base is accepted as well and flagged for the worker to apply by intent, because a hand-carried round trip can take hours (#1064: sent 08:13, answered 18:03) and the app changes all day; and the rules tell the agent not to answer `insufficient` when it can see the function, and to name identifiers rather than subjects when it must. the id is only insisted on when more than one request is open on the issue, since with a single one there is nothing else an answer could be about (#1090 echoed `1064-1bab`, an id from another issue, and a usable answer naming four functions was discarded); and the base is only checked for a `patch`, which has to apply to known code, not for an `insufficient` or `answer` that carries no hunks. A request is also budgeted as a whole: `relay_max_request_chars` (30000), of which attached files take at most `relay_max_extra_chars` (12000) and any one file `relay_max_file_chars` (8000), and the excerpt is served first because it is the point. #1090's request went out at 43,166 characters with a gel densitometry suite attached to a job about the Construct sequence field, and came back `insufficient`. A passing patch becomes an issue labelled `from-relay`, `owner-approved` and `for-claude-first`; the patch itself is never committed by the manager. Code: `tools/local-manager/relay.py`, test `tools/local-manager/test_relay.py`. Settings: `relay_label`, `relay_expire_hours`, `relay_max_rounds`, `relay_context_lines`.

**Direction board (#222).** The local model, Gemini and ChatGPT hold a team meeting there by themselves: every 4 hours while the owner's PC is on (`board_every_hours`), after every 5 merged PRs (`board_every_merges`), when fewer than 15 jobs are queued (at most hourly), weekly on Sunday, or when the owner comments **Discuss: <topic>**. Each meeting opens with a review of the work in progress (what is running, stuck, sent back by the gate or merged, and how the board's own earlier proposals turned out), then each adviser proposes up to 3 directions with their case (problem, evidence, risk, rejected alternative), debates them for 2 rounds (reading the whole discussion, arguing for or against, revising or withdrawing its own), and votes 1 to 5. The meeting is posted live: opening, each round, decision. **Board memory:** every meeting sees what was merged in the last 3 weeks, all open work, and the fate of earlier board ideas (done, open, declined, or closed as a duplicate), and is told not to propose them again. Before an idea is adopted, a duplicate check compares it with that memory: a cheap word match first, then Gemini Flash Lite for close calls only. A duplicate is not adopted, and the decision post says what it repeats. Proposals with an average of 3.5+ and no score below 3 are adopted as `from-board` issues carrying the votes and the debate, up to 5 a meeting and only while fewer than 25 jobs wait. Every adopted idea goes straight to `jules-queue`, so the work starts at once (with `board-approved` too when all three advisers scored it 4 or more, `board_go_score`). **No board change to the app merges without Patrick's OK (his choice); PRs that only touch tests or docs still merge automatically.** A PR for a `from-board` issue that changes the app goes through the Test suite, the gate and the AI lead review. Then, instead of merging, it gets `awaiting-owner` and a **Ready for your OK** comment. Patrick replies **OK** on the PR (the manager adds `merge-ok` and merges it) or **No** (the PR is closed and the issue gets `owner-declined`). The Jules leader never merges a PR labelled `awaiting-owner`. The manager posts with the owner's token, so it reads only comments without its own signature as his. The owner can reply **No n** to drop an adopted one or **OK n** to add one, but nothing waits for him. **Relay route:** an adopted idea that not every adviser scored `board_go_score` or more (at most `board_relay_max`, 2, a round) is labelled `relay-from-board` instead of `jules-queue` and becomes an offline relay request for Patrick (`docs/RELAY.md`); if it expires unanswered it goes to `jules-queue`.

- **Jules** works from issues labeled `jules`.
- **Claude** reviews PRs changing the app automatically and is called on any PR with `@claude`.
- Agents never push to another agent's branch: a revision goes on a new branch.
- Several PRs may change the HTML file at once (up to 8). A PR that conflicts with main is rebuilt on main by the local manager when its own diff still applies, and otherwise restarted by the gate.

## The Jules leader (automatic queue)

`.github/workflows/jules-leader.yml` is rule-based, with no AI:

- **`from-patrick`:** issues the owner reports. They start before any other queued issue. `docs/GOALS.md` sets the order of everything else.
- **`jules-queue`:** issues with this label get a Jules session through the Jules API, at most 15 at a time (Jules Pro allows 100 tasks a day), of which at most 8 may change the app (`MAX_APP`): the app is one file, so more parallel edits mostly collide at merge time. Label: `jules-running`. The first prompt states the evidence rule (a change to a reported number or text needs a UI-level check that fails on main and passes on the branch), because a missing check caused most gate rejections.
- **Stale base:** once 6 PRs have merged into main since a session started (`REBASE_AFTER`), the leader asks it once to update its branch to the current main and rerun its suites before committing.
- **Questions:** the first prompt already tells Jules the standing rules (never skip a check; if `compare.js` is too slow, run the suites it changed and open the PR). A question about skipping or slow tests, or whether to go ahead and open the PR, that names no scientific value is answered at once by rule. For any other question the leader posts it on the issue and gives the local manager 10 minutes to answer (`Answer for Jules:`, relayed on the next check). If none comes, it tells Jules to decide by these rules and open the PR. After 6 replies the issue gets `needs-coordinator`. A person (or the coordinator) can answer instead by commenting on the issue with a line starting `Answer for Jules:`. The leader passes that text to the running session, but **only from the owner, a collaborator or an organization member** (GitHub's `author_association`, which the commenter cannot set). The repository is public, so until 2026-11-05 the only test was that the author was not a bot, and any stranger could steer a running coding session that can push. One outside comment did appear that day, on #1066. Anything from anyone else is ignored and noted once in the run log.
- **Checks:** every 3 minutes while work is queued or running, and whenever Jules comments or a test run finishes.
- **Failures:** a failed session is retried with "work in smaller steps", up to 3 attempts. After that the issue gets `needs-coordinator`.
- **Slow sessions:** a session gets one nudge to wrap up after 6 hours. After 12 hours (working or stuck waiting), its slot is freed: it is restarted as the next attempt in smaller steps, and after the last attempt the job goes to Codex (`for-codex`).
- **Finished:** the issue gets `jules-done` and a link to the PR.
- **Merging:** a PR that touches only `tests/`, `docs/`, `README.md` or issue templates, with a clean Test suite report, is merged automatically. Any other PR gets `needs-coordinator`.
- **Follow-ups:** "New checks failing" in a merged PR's test report, and "Ready-to-file issues" in a merged `docs/*audit*.md`, become issues labelled `needs-triage`. A person or the coordinator moves them to `jules-queue` after checking scope and scientific impact.

The older `jules` label still starts Jules directly, without the leader's retries.

## Reviewing a pull request

When reviewing, check:

- That the change does what the linked issue asked, and nothing more.
- Correctness, especially of parsing, numerical calculations and figure output.
- Backward compatibility with saved settings and projects.
- That the PR reports test suite results, and that no check was weakened or removed without a reason.
- That README claims match what the code actually does.
- No new external network requests or dependencies.

Report findings with the file and line, and skip pure style preferences.

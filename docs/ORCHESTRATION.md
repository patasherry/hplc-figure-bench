# Orchestration: how the agents divide the work

This is the full account of the automation around Protein Purification Bench: every worker, queue label, setting and the incidents behind them. It was moved out of `AGENTS.md` on 2026-11-12 so that coding workers stop reading about 6500 words of it on every job. `AGENTS.md` keeps the rules a worker needs. Update this file when you change how the automation works.

## How a request from Patrick gets done (2026-11-12)

Patrick asked for a cleaner hierarchy after his cloning request, posted on the Direction board, was rewritten by the board into four vague proposals and then sat unseen. The rules now:

1. **One door.** A request is a `from-patrick` issue, opened with the Request form (`.github/ISSUE_TEMPLATE/request.yml`) or filed by Claude from a chat, always in his own words. The Direction board is for discussion he asks for (`Discuss: ...` on #222). It is not a way to ask for work, and nothing rewrites a request before a worker reads it.
2. **Two sizes.** The queue leader (no AI) takes every new `from-patrick` issue. A short one gets `queued` and `owner-approved` and goes to the workers. A long one (over 2,500 characters, or the form's big-request box ticked) gets `needs-plan` and waits for one planning pass by the lead (Claude), who splits it into small, separately testable jobs, building shared structure first and data second, as the cloning engine did (#1403). No worker starts a `needs-plan` issue.
3. **One status page.** The leader keeps one issue labelled `status-page` up to date: what waits on Patrick, what waits on Claude, what is stuck (no movement for 3 days), his requests in progress, what was finished in the last 14 days, and whether the workers are up. When something newly needs him or gets stuck, the leader mentions him there once, so GitHub notifies him.
4. **No orphans.** An open issue with no state label and no open PR cannot be seen by any worker. The leader finds these every run: his own are put through intake again, the rest get `parked`.
5. **Machine-made work is parked, not queued.** Follow-up issues the leader files from failing new checks and audit reports are labelled `parked`. The board no longer meets on a timer (`board_auto: false`) and the usability walks are off (`ux_every_hours: 0`). Adding `queued` to a parked issue starts it.
6. **His requests go first.** Every background worker sorts `from-patrick` jobs ahead of the rest, in whichever queue they sit.

The lead's part: when Patrick says "work through my status page" or "plan my requests", read the status page, plan each `needs-plan` issue into jobs (label them `queued`, `from-patrick`, `owner-approved`, link them from the request and close the request only when all of them are done), and settle anything under Waiting on Claude.

## Current routing (2026-11-12)

Patrick's PC is on about 10 hours a day on average (his estimate, 2026-11-12, after first saying a couple of times a week), and he wants Claude and Codex used as little as possible. The Antigravity API route in the cloud has refused every call since 2026-11-09 with a storage-quota error, so in practice the PC's `agy` CLI does the coding and PC-off hours do none. So:

1. **Antigravity is the first worker, everywhere.** The queue leader routes every `queued` issue to `for-antigravity`. With the PC off, the Antigravity API route in the cloud manager serves that label. With the PC on, the `agy` CLI does too, up to `max_agy_jobs` (20) a day.
2. **Antigravity gets its own second attempt.** A job it failed once, or one the gate sent back with notes, runs the second time on `agy_model_retry` (default `""`, which takes the sign-in's default model, the stronger one on AI Pro) instead of `agy_model` (3.8 Flash).
3. **The gate sends a failed Antigravity PR back to the queue with its notes**, up to twice, as it did for the first worker before. Until this change such a PR went straight to `for-claude-code`.
4. **Codex is a retry worker.** From the open queue it takes only issues carrying `ag-returned` (`codex_queue: "returned"`, or `"all"` for the old behaviour), plus `for-codex` and `for-claude-code`. It no longer sits on the Direction board (`board_codex: false`), and its helper calls are capped at `max_codex` (10) a day.
5. **Claude is last.** Claude Code on the PC takes at most `max_claude_jobs` (1) a day. The Claude API worker takes at most 1 a day. The automatic Claude review of every app PR is off: `.github/workflows/claude-code-review.yml` runs only when started by hand with a PR number. `@claude` on a PR still works. Advice on `for-coordinator` items comes from Gemini first.

Jobs that carry `ag-returned` wait in `queued` for a day the PC is on. That is intended: waiting costs nothing, and the alternative is a Claude job.

The sections below predate this and describe each part in detail. Where they disagree with the list above, the list is right.

## The parts in detail

`docs/GOALS.md` is the owner's list of priorities. Every agent weighs its work by it. Once a day the lead posts a **Lead check-in** on issue #17, and the local manager follows the newest one.

A coding agent's questions go up a ladder, run by the local manager on the owner's PC: the local model tries three times (quick, then twice more with the code in front of it, each answer checked by a second local pass), then Gemini (given the code it needs), then ChatGPT (Codex, read-only), then the local model once more with their notes, then Claude Code (read-only), and only then the lead (`for-coordinator`). Each answer says who decided and the path it took. Anything that would change a reported number goes to the owner (`needs-owner`) instead. The owner answers on the issue with a comment starting **OK** (the manager labels it `owner-approved` and queues it) or **No** (`owner-declined`, taken out of the queue). Merging app changes stays with the lead, and a `needs-owner` change is merged only with `owner-approved`.

**Empty pull requests are never merged.** A PR that changes no files passes every file and test check vacuously, so until Nov 5 such PRs were auto-merged and closed their issues ("Fixes #N") while the bug stayed in the app: #770 and half of #772 were lost that way, among 12 empty merges. The manager's gate now closes an empty PR and puts its issue back in `queued`, and the queue leader flags one for the coordinator instead of merging. That check runs **before** the gate waits for the Test suite, because an empty PR touches neither the app nor `tests/`, so the suite never runs on it and the wait never ends: #1016, #1058, #1076, #1080 and #1081 sat open for up to a day that way, each with a commit message claiming a fix and nothing in the commit. Zero files needs no test run to judge. If a fix really is already on main, say so on the issue and close the issue directly, without a PR.

**Automatic review gate.** When the Test suite finishes on a PR that changes the app, the local manager checks it with plain code: only the app, `tests/`, `docs/`, `README.md` and `.gitignore` change; no regressions; at least one check fails on main and passes on the PR ("Checks this PR fixes"); no check it adds fails on the PR; no existing check is deleted or commented out; no test reaches into `window.__HFB`; `expected.json` is not rewritten; no merge conflict. A PR that fails is closed, the reasons are added to its issue, and the issue goes back to `queued` (at most twice, then `for-coordinator`). A PR that passes and doesn't change a reported number (its issue has neither `needs-owner` nor `owner-approved`) is **merged by the manager**, one per pass. One that changes a number gets `ready-for-lead` for the lead's review, plus `needs-owner` if the owner's OK is still missing.

The gate also checks PRs that only change tests or docs when they carry stray files. When the only problems are stray files (scratch scripts, logs) or a merge conflict, the manager **rebuilds the PR itself**: it applies just the PR's own app and test changes on the current main as a new PR on `claude/issue-N`, closes the original, and the new PR goes through the tests and the gate. No worker retry is spent on that. The same rebuild covers two cases where GitHub never runs the tests: a PR that conflicts with main for 30 minutes with no test run, and a finished Copilot cloud-agent PR (a draft that asks the owner for review), whose tests GitHub holds for a person to approve. The rebuild carries only the app, `tests/`, `docs/` and `README.md`, so workflow changes never run unreviewed.

**Claude Code jobs.** When the queue workers and then Copilot are out of tries (the gate sent the job back twice and Copilot's attempt failed too), the issue gets `for-claude-code`. The local manager runs Claude Code on the owner's PC in a separate git worktree (`~/hfb-work/issue-N`, from `origin/main`), limited to editing files and running the test suites. Each job's worktree gets a link to the main checkout's `tests/node_modules` (a junction on Windows, never committed, removed before the worktree is deleted) so the agent can run the suites before the PR opens. The same holds for Copilot CLI jobs. The manager checks that only the app and `tests/` changed, commits, pushes the branch `claude/issue-N` (with `copilot/issue-N` for Copilot CLI jobs and `antigravity/issue-N` for Antigravity jobs `openclaw/issue-N` for OpenClaw jobs and `codex/issue-N` for Codex jobs, the only branches it ever pushes) and opens the PR. That PR goes through the Test suite and the gate like any other, and if it fails it goes to the lead. At most 3 jobs a day (`max_claude_jobs`). Claude Code (read-only) is also the last step of the question ladder before the lead.

**GitHub Copilot coding agent (off by default).** Patrick has no Copilot credits, so `copilot_mode` is `off`: no job goes to Copilot, a job whose turn would be Copilot's (`for-copilot`) goes straight to Claude Code, and the Copilot CLI is not used. Setting `copilot_mode` to `auto`, `cloud` or `cli` in the settings file restores what follows. A second coding worker, started by the local manager with the owner's token (the API takes only user tokens, so the leader can't). Whenever a job waits in the queue (`copilot_when_queue`, 1), the manager assigns the newest one (not `needs-owner` or `from-patrick`) to `copilot-swe-agent[bot]`, with the AGENTS.md rules as custom instructions: at most 4 at a time (`copilot_at_once`) and 10 a day (`max_copilot_jobs`). Copilot also gets the **next try when the queue workers are out of tries** (`for-copilot`), before Claude Code. The issue gets `copilot-running`, then `copilot-done` when Copilot's PR ("Closes #N") appears. Copilot's PRs go through the Test suite and the gate like any other. One that fails, or a retry with no PR after 8 hours, goes to Claude Code (`for-claude-code`). An ordinary job with no PR after 8 hours goes back to `queued`. It needs a paid Copilot plan (the owner has it through GitHub Education). After a refusal the manager backs off for 6 hours, or until it restarts, and sends retries straight to Claude Code. When Copilot takes a job but posts that it is unable to start (for example out of GitHub AI Credits), the manager hands the job back at once (to the queue, or to Claude Code for a retry) and pauses Copilot for 24 hours, also across restarts. While the cloud agent is paused, the manager runs the **Copilot CLI** on the owner's PC instead (`copilot_mode`, `auto` by default; `cloud` or `cli` to use only one): one job at a time in its own worktree (`~/hfb-work/copilot-N`), allowed to edit files and run only node, python and read-only git. The manager checks that only the app and `tests/` changed, commits, pushes `copilot/issue-N` and opens the PR, which the gate treats like the cloud agent's. It shares the Copilot daily cap.

**Google Antigravity agent.** A third coding worker, reached through the Gemini API (Interactions API, agent `antigravity-preview-09-2026`, the same `GEMINI_API_KEY`), so it runs from the PC manager and the cloud manager alike.

**Google Jules was removed on 2026-11-12.** Google announced the shutdown on 2026-10-29: sessions ran until 2026-11-11, the service is read-only until 2026-12-31, then closes. Nothing needed exporting, because the code, branches and pull requests are on GitHub.

What went: the Jules API client and session handling in the leader, the per-issue JSON state comment, the retry and nudge logic, the question relay (`Answer for Jules:`), `jules_questions()` and `jules_failed()` in the manager, `tests/tools/test_leader.js`, and the `JULES_API_KEY` secret. The question **ladder** stayed, since it is general (local model, then Gemini, then Codex, then Claude Code, then the lead) and the `--ask` console path uses it.

**The queue label was renamed `jules-queue` to `queued`.** Every consumer reads both names for a transition so nothing in flight is stranded, and only `queued` is ever written: `QUEUE` and `QUEUE_OLD` in the manager, `L.queue` and `QUEUE_OLD` in the leader. `jules-running` and `jules-done` stay in `ALL_RUNNING` and `ALL_DONE` on purpose, because those sets are only removed from or tested against, so a stale label from before the removal gets stripped. Drop `QUEUE_OLD` once no open issue carries the old name.

Every queue listing drops pull requests, because GitHub's issues API returns them too. `issues()` in the manager does that filtering, and a listing that calls `gh(...)` directly does not: on 2026-11-09 a coordinator-queue cleanup that skipped the filter routed five open pull requests (#1300, #1301, #1302, #1315, #1317) to `for-antigravity` as if they were unstarted jobs. No worker took one, and both `for-coordinator` listings now go through `issues()`. The prompts in `docs/ANTIGRAVITY.md` say the same, since their `curl` fallback hits that endpoint while `gh issue list` does not.

**Antigravity takes the coding work (Patrick's choice, 2026-11-05).** The queue leader routes every `queued` issue to `for-antigravity`. The routing is in the leader because the leader is what races: it checks every few minutes and used to start the job before the manager saw it, which is why the API route had produced no pull request at all by Nov 5 while the queue looked busy. `AG_TAKES_APP=0` in the leader's environment turns the split off.

Three things stop a job getting stuck on that label. A `for-antigravity` job nobody has started within `antigravity_stall_minutes` (45) returns to the queue, and so does every such job at once while the Gemini API is paused, which it is for 6 hours after a refusal. A job Antigravity fails goes back to it for one more try (`antigravity_max_tries`) and then to the queue. Either way it is labelled `ag-returned`, which stops the leader routing it to Antigravity again, so a job can never bounce between the two.

**The Antigravity CLI on the owner's PC (`agy`), the working route.** Patrick has Google AI Pro, and the Antigravity CLI is included at every subscription tier, drawing on the subscription quota through the sign-in an interactive `agy` session caches, not on the Gemini API key whose project has refused every Interactions call. It runs headless, so the manager treats it like Codex and OpenClaw: one job at a time in its own worktree (`~/hfb-work/agy-N`), `agy -p` with `--output-format text`, `--print-timeout`, `--model` and `--dangerously-skip-permissions` (see below), at most `max_agy_jobs` (8) a day, stopped after `agy_hours` (2). It runs on **3.8 Flash** (`agy_model`, default `gemini-3.8-flash`), Patrick's choice over the Gemini 4 Argon the sign-in defaults to, to spend less of the AI Pro quota per job. `--model` is the only headless way to pick one, since `/model` is interactive; `agy models` lists the names a build accepts, and `agy_model: ""` drops the flag and takes the sign-in's default. The manager logs the model when a job starts, so a name this build rejects shows up as that and not as a mystery failure. **Its queue is `for-antigravity`**, the same label the queue leader fills, so the CLI serves the coding queue whether or not the API ever works. It pushes `agy/issue-N`, and the gate treats its PRs like Copilot's. A failed CLI job is handed back with **`ag-returned`**, like the API route's, and `for-antigravity` removed: without that the queue leader re-labelled the issue `for-antigravity` within three minutes, and the worker's own-label branch does not consult the attempt count, so the CLI took the same failing job again and again until its daily cap was gone. The count is stored as a number too, since a timestamp was always read back as one attempt and `antigravity_max_tries` was never reached. The restart sweep hands back the same way. Needs the CLI findable and one interactive sign-in first; `agy_jobs_on: false` turns it off. `agy_exe` names its full path when PATH does not have it, which on Windows is easy to hit, since it is a shim (`agy.cmd`) and a manager started from a shell whose PATH predates the install will not see it. `have_agy()` also treats a start that actually worked as proof for 7 days: on 2026-11-05 the CLI opened #1070 at 21:26 and two hours later the stall guard swept six jobs back to the queue saying it was not installed, so a missed PATH lookup must never read as "not installed" again. The reason a sweep gives is now the real one, naming PATH, the off switch or the cloud copy.

**It runs with permission prompts skipped, because on Windows nothing else works.** In headless mode an approval nobody can answer is *soft-denied*: the run continues, exits 0 and has changed no files, which the runner then reports as "no changes". On Windows the CLI still uses the older permission system, and `permissions.allow` rules in `~/.gemini/antigravity-cli/settings.json` do not reach it: on 2026-11-05 both `write_file(*)` and a concrete `write_file(/Users/Patrick)` were ignored and the smoke test auto-denied the write, while `--dangerously-skip-permissions` edited the file at the first try. So `agy_yolo` defaults to true. This is the least contained worker here, less than Codex's `workspace-write`: during a job the agent may run any command on the PC, not only writes inside the worktree. What limits it is that the job runs in a throwaway worktree (`~/hfb-work/agy-N`), the task file is the manager's own, and the manager checks which files changed before it pushes. `agy_sandbox` would add `--sandbox` for containment but is **off** by default: it is unverified on Windows, and an unsupported flag fails the same silent way the permissions did. Turn it on once a smoke test shows the CLI still edits a file with both flags.

Because the CLI takes one job at a time, a backlog on `for-antigravity` is not a stall: the stall guard keeps the newest `agy_backlog` (6) for it and returns the rest to the queue, and sweeps the lot only when the API is paused *and* the CLI is not installed.

**The API route was refusing every call, and it was our own sandboxes.** Every attempt from Nov 1 to Nov 5 returned `HTTP 429 Too Many Requests` on the first call of the day with no usage behind it, which was read here as the agent having no quota on this key's tier. That was wrong. Once `gem_api` started reporting the response body, on Nov 6, the message turned out to be `Project environment storage quota exceeded`: every call asks for `environment: 'remote'`, which creates a sandbox, and the API keeps each sandbox for **7 days** after its last activity whether or not anything needs it. At up to 40 jobs a day the project filled with our own leftovers. Nothing was wrong with the tier.

`ag_sweep_envs()` now lists the environments and deletes those untouched for `antigravity_env_keep_hours` (6, safely more than the 3-hour interaction cap, and it keeps anything whose timestamp it cannot read). On a refusal naming the environment storage quota the manager sweeps and retries on the next pass, at most one sweep an hour, instead of counting a refusal. Any other refusal still counts (`antigravity_refusals_before_dead`, 3) and then backs off for `antigravity_dead_hours` (24) rather than retrying every 6 hours forever, and says so once on #17, now distinguishing the two causes. A call that succeeds clears the streak by itself. The desktop app and the `agy` CLI serve the queue either way.

**The desktop app** (`paste-to-antigravity`, called `for-antigravity-app` until 2026-11-05): the only Antigravity path that has ever landed a PR here (#759, #765, #1048, #1049, #1050). `docs/ANTIGRAVITY.md` holds the ways to give it work. The **scheduled prompt** there is the preferred one: Patrick pastes it once per session and the agent sets up a task in that session which repeats every 30 minutes, each firing pulling main, listing the `for-antigravity` queue itself and taking at most one job, skipping anything that already has a PR, is held by another worker, or carries `needs-owner` without `owner-approved`, and stopping after 8 PRs a day. Re-reading the queue every firing is what keeps two runs off the same job. A one-off version that empties the queue now and stops is there too. Per-issue prompts are **off** by default (`antigravity_app_at_once` and `antigravity_app_at_once_dead`, both 0), because the scheduled prompt already covers every job on the label and a per-issue prompt then only asks Patrick for something that is already handled. Set `antigravity_app_at_once` to 2 to get them back: the manager then labels that many app-changing jobs `paste-to-antigravity` and posts a ready-to-paste prompt on each. The label name says whose action it is, and `for-antigravity` never does: that one is a worker queue, served by the CLI, the API route and the scheduled app session, and it needs nothing from him. Nothing waits on Patrick: the stall guard returns what the app route cannot hold to the queue, and the label clears itself when a PR appears or another worker takes the job. Both loops in `antigravity_app()` test that with the same `ag_app_done()`, because when they disagreed the cleanup dropped the label and the fill loop re-posted the prompt on the same pass: #1038 collected four copies while PR #1048 was already open.

It also takes jobs whose worker is away: `for-copilot` jobs while Copilot is paused, and, in the cloud, `for-claude-code` jobs while the PC is off. Otherwise, while at least 2 jobs wait in the queue (`antigravity_when_queue`), the manager hands the newest one (not `needs-owner` or `from-patrick`) to Antigravity as a background job: at most 6 at a time (`antigravity_at_once`), 3 handed over per pass (`antigravity_per_pass`) and 40 a day including reviews (`max_antigravity_jobs`), all raised on Nov 5 because it now owns the app-changing queue, label `antigravity-running`. The agent clones the public repository in Google's sandbox, follows AGENTS.md and returns its change as a diff, and never gets a GitHub token. On a later pass the manager applies the diff on the current main, keeps it only if every changed file is the app or under `tests/`, pushes `antigravity/issue-N` and opens the PR (`antigravity-done`). The gate treats it like a Copilot PR, so a failure goes to Claude Code. A job that fails, gives no diff or runs over 3 hours goes back to `queued`. If the API refuses, Antigravity is paused for 6 hours.

**OpenClaw on the owner's PC (the local model as a coder).** The local model is a **manager** by default again (`local_role: manager`): it answers coding agents' questions first, triages, writes first-pass review notes and sits on the board, as before. With `local_role: coder`, the local Ollama model writes code through OpenClaw instead of managing. Gemini then answers those questions and triages on the PC as in the cloud, the local first-pass review notes are off, and the board meets with Gemini and ChatGPT (strong consensus then means every adviser present scored 4 or more). The PC manager runs `openclaw agent exec --message-file HFB_TASK.md --cwd <worktree>` in the background, one job at a time (`max_openclaw_jobs` 8 a day, stopped after `openclaw_hours` 1.5), in `~/hfb-work/openclaw-N` with the test libraries linked in. It takes issues labelled `for-openclaw` (jobs meant for it), and otherwise only small jobs from `queued` that nobody has started after 10 minutes (`openclaw_wait_minutes`), so it works only where it is the faster option. Gemini Flash Lite decides once per issue whether a job is small: one test, a message or label fix, or one function, about 50 lines at most. Three runs on a large feature (#500) showed a 30B local model can't work across the whole app file. It then also failed two small test-only jobs (#514, #515) within two minutes, so OpenClaw jobs are **off** by default (`openclaw_jobs_on: true` in the settings file turns them back on). When the job ends, the manager checks that only the app and `tests/` changed, commits, pushes `openclaw/issue-N` and opens the PR, which the gate treats like Copilot's. A failed job goes back to the label it came from and is not given to OpenClaw again. `local_role: manager` restores the old split.

**Codex on the owner's PC (ChatGPT plan).** The same background runner as OpenClaw also runs `codex exec --sandbox workspace-write -C <worktree>` as a coding worker, one job at a time (`max_codex_jobs` 6 a day, `codex_hours` 1.5), in `~/hfb-work/codex-N` with the test libraries linked in. It takes `for-codex` issues first, then `for-claude-code` jobs (it runs before Claude Code in each pass, so Claude Code only gets what Codex couldn't do), then `for-copilot` jobs while Copilot is paused, then the newest `queued` job. It pushes `codex/issue-N`, and the gate treats its PRs like Copilot's. A failed job goes back to its label and isn't given to Codex again. An issue someone labels `for-openclaw` or `for-codex` always gets a fresh try, even after an earlier failure, and if that try fails it goes to `queued`. Codex uses a light model for routine work (questions, board, advice and ordinary coding jobs; `codex_model`, default `gpt-5.6-terra`) and a heavy model only for hard jobs, those from `for-claude-code` and `for-codex` (`codex_model_heavy`, default `gpt-6-astra`), the owner's choice to save his ChatGPT allowance. `codex_effort` sets the reasoning effort. The PC manager's hourly self-update waits while a Codex or OpenClaw job is running, so a restart never cuts one off. When an update is over 3 hours late, no new coding job starts until it is done. The manager's folder always stays on `main`: if another tool left it on a branch, the update switches it back (when there are no unsaved changes). Other tools, such as the Antigravity app, use their own clone.

**Claude API worker (GitHub Actions, billed to API credits).** `.github/workflows/claude-api-worker.yml` runs Claude Code (Sonnet, at most 80 turns) on GitHub Actions with the repository secret `ANTHROPIC_API_KEY`, so it spends Patrick's Anthropic API credits and not his Claude plan. Without that secret it falls back to `CLAUDE_CODE_OAUTH_TOKEN` (his plan, then his usage credits if they apply) (the Claude plan limits are why the scheduled cloud worker below is paused). It starts when an issue is labelled `for-claude-cloud`, every 4 hours, or by hand (Actions, Run workflow, with an optional issue number). Each run takes one job: a `for-claude-cloud` issue first, else a `for-claude-first` audit finding the PC hasn't taken in 2 hours, else a `for-claude-code` issue nobody has taken for 6 hours, never one waiting for the owner's OK or already running. At most 2 jobs a UTC day (`MAX_PER_DAY` in the workflow). Claude only edits files and runs the suites. The workflow then checks that only the app, `tests/`, `docs/` and `README.md` changed, pushes `claude/issue-N` with `HFB_TOKEN` (so the Test suite runs) and opens the PR, which goes through the gate like any other. A job it can't finish goes to `for-coordinator`. Labels: `claude-cloud-running`, then `claude-cloud-done`.

**Claude Code cloud worker (scheduled task, paused).** Paused on Oct 31: scheduled cloud runs draw on Patrick's plan limits, not on his API credits. When it is turned back on, a Claude Code cloud session starts on a schedule, with no PC needed. Each run takes one job: an issue labelled `for-claude-cloud` first, then `for-claude-code` (the queue workers and Copilot are out of tries), then the newest `queued` job that has no `needs-owner` (without `owner-approved`) or `from-patrick`. It labels the issue `claude-cloud-running`, works on `claude/issue-N` from main, runs the suites it touched, opens the PR (`claude-cloud-done`), and sends a job it can't finish to `for-coordinator`. Its PRs go through the Test suite and the gate like any other. Label an issue `for-claude-cloud` to send it there on purpose.

**Usability tester (scheduled task, paused).** Paused on Oct 31 for the same reason; the usability scopes below do this job on the PC with the local model. When it is on, a Claude Code cloud session starts every 4 hours and uses the app the way a person would. It drives it with Playwright on the synthetic data, works through one journey per run, rotating through first visit, workflow, branches, gels, SEC, zoom and full view, phone width and dark mode, and projects, and looks at its screenshots. It fixes at most one small UI-only problem itself (an issue labelled `from-ux-test`, then a PR on `claude/ux-N` that goes through the Test suite and the gate). It files up to 3 more problems as `from-ux-test` + `needs-triage` issues, after checking for duplicates, and never fixes a number itself. It posts a **Usability test report** on the Direction board (#222) for the advisers' next meeting.

**Usability scopes (PC manager, local model).** Every 3 hours while the PC is on (`ux_every_hours`, 0 turns it off), the manager walks one test scope from `tests/ux/scopes.js` through the app with `node tests/ux/scope.js <scope> <folder>`. The scopes are use cases (first visit, workflow, layout and dragging, gels, SEC, zoom and full view, phone width and dark mode, projects), taken in turn. The runner uses synthetic data only, takes a screenshot after each step, and records with plain code what a user would hit: steps that could not be done, page errors, sideways scrolling, cut-off hints and labels, controls off the screen edge, and overlapping figure text. The local model then reads each screenshot as a first-time user and notes up to 3 problems (Ollama vision; skipped if the model can't take images). One screenshot gets `ux_vision_seconds` (180, down from 600: a timeout costs the pass that whole time and every duty behind it waits), and after `ux_vision_give_up` (2) **failed** calls in a row the walk finishes on plain checks alone. A screenshot the model read and found nothing wrong in is not a failure and never counts towards that, which is the common case. The report becomes a `ux-report` issue, one per scope, with later walks added as comments. It also becomes the Direction board's next topic: the advisers check which findings are real and propose fixes, adopted like any board proposal. The scope files are not a suite, so CI never runs them. Add a use case by adding a scope.

**AI lead review.** PRs that pass the gate but change a reported number (`ready-for-lead`, no regressions, and the issue `owner-approved` or `board-approved`) are reviewed by the AI the owner picks with a comment on #17 starting **Reviewer:** `gemini` (the default), `antigravity` or `claude`. The newest such comment wins, on the PC and in the cloud. Gemini reads the issue, the PR, the test report and the diff (Flash models first, `review_models`). Antigravity checks the PR out in its sandbox and can run the suites, in the background. The verdict is posted on the PR with the commit it covers:
- **merge:** the manager merges it, one per pass.
- **send_back:** the notes go on the issue, the PR is closed and the issue returns to `queued`.
- **lead:** it gets `for-coordinator` for Claude.
With `Reviewer: claude` nothing is reviewed automatically and the lead handles them as before. If Antigravity is refused, the review falls back to Gemini.

**Cloud manager.** `.github/workflows/cloud-manager.yml` runs the same manager (`manager.py --cloud`) on GitHub Actions every 10 minutes and after each Test suite run, so work keeps moving while the owner's PC is off. The PC manager refreshes a heartbeat comment on the tracking issue (#17) every 5 minutes, and the cloud copy stands aside while it is under 20 minutes old (`cloud_standby_minutes`). In the cloud, Gemini (repository secret `GEMINI_API_KEY`) stands in for the local model. The cloud copy runs owner replies, the gate with auto-merge and rebuilds, the Copilot cloud agent, triage and the stuck check. Board meetings, local first-pass reviews, Claude Code jobs, the Copilot CLI, advice and the digest stay on the PC. It posts with the owner's fine-grained token (secret `HFB_TOKEN`), so its rebuilt PRs trigger the tests. Its memory (the state file) is kept between runs in the Actions cache. GitHub rarely fires its 10-minute schedule, so the queue leader starts it whenever its last run is over 10 minutes old.

**Claude Science inbox (#782).** Patrick posts findings from Claude Science's independent audits there, one per comment (or several, each under its own `# ` heading), pasted or attached as `.md` or `.txt` files. The manager, on the PC or in the cloud, files each as an issue labelled `from-patrick`, `from-science`, `owner-approved` and `for-claude-first`: posting there is his OK. Claude Code merges most numeric fixes at the first try (93% against 52% for the queue workers), so these go to Claude first: Claude Code on the PC takes `for-claude-first` before `for-claude-code`, and the Claude API worker takes it after 2 hours if the PC hasn't. A first try that fails, at the job or at the gate, goes on to `queued` (not to the lead), and so does one no Claude worker has taken in 24 hours. The managers mark every reply on #782 with the comment it answers (`<!-- science-src N -->`) and also read the inbox links in filed issues, so the PC and cloud copies never file the same finding twice. Comments addressed to `@claude` are left to the Claude workflow. A PR that changes a reported number still goes through the gate and the AI lead review. Before filing, the duplicate check used by the board compares the finding with open issues and recent PRs, and a duplicate is only linked. `File anyway: <title>` overrides that, and a comment starting `Note:` is ignored. Findings must use synthetic data only (`science_inbox` in the settings file, 0 turns it off).

**Offline relay (`docs/RELAY.md`).** For questions an agent with no access to the repository can answer. Patrick labels an issue `needs-relay`; the manager (PC or cloud) posts a self-contained request block with a numbered excerpt of the app, and Patrick carries the agent's response block back as a comment. The manager posts a request only for a label Patrick added and files work only from a response Patrick pasted. Six checks run in order; the one that matters is that every hunk's old side is still verbatim in the app at current main, so a stale patch is refused and a fresh request is emitted (at most `relay_max_rounds`, 1). The aim is one round: the excerpt is picked by explicit range, then line number, then the functions the text names, then the phrases it quotes that appear verbatim in the app (a UI issue quotes its own button text), then the app sections whose subject matches its words (rare words count for more), capped at `relay_max_lines`; every request carries `tests/lib/harness.js` (a patch must bring a test, and without the harness an agent writes it against `@playwright/test`), and a job about checks gets a worked suite too; the response parser is deliberately loose about blank lines, fence style, tags, sha length (a `base` is compared by prefix, as git does) and **indentation**, since correct answers kept being thrown away: two on #1015, one for a blank line after `patch:` and one for echoing the full commit sha, and two on #1064, whose patch sat exactly at the lines its own header named and carried three spaces where the app has two. A hunk now matches on its content as a contiguous run of lines, ignoring each line's leading and trailing whitespace, since a filed patch is carried out by a coding agent and never fed to `git apply`; order and contiguity still hold, so an invented hunk is still caught. A hunk that matches only the app as it stood at the request's own base is accepted as well and flagged for the worker to apply by intent, because a hand-carried round trip can take hours (#1064: sent 08:13, answered 18:03) and the app changes all day; and the rules tell the agent not to answer `insufficient` when it can see the function, and to name identifiers rather than subjects when it must. the id is only insisted on when more than one request is open on the issue, since with a single one there is nothing else an answer could be about (#1090 echoed `1064-1bab`, an id from another issue, and a usable answer naming four functions was discarded); and the base is only checked for a `patch`, which has to apply to known code, not for an `insufficient` or `answer` that carries no hunks. A request is also budgeted as a whole: `relay_max_request_chars` (30000), of which attached files take at most `relay_max_extra_chars` (12000) and any one file `relay_max_file_chars` (8000), and the excerpt is served first because it is the point. #1090's request went out at 43,166 characters with a gel densitometry suite attached to a job about the Construct sequence field, and came back `insufficient`. A passing patch becomes an issue labelled `from-relay`, `owner-approved` and `for-claude-first`; the patch itself is never committed by the manager. Code: `tools/local-manager/relay.py`, test `tools/local-manager/test_relay.py`. Settings: `relay_label`, `relay_expire_hours`, `relay_max_rounds`, `relay_context_lines`.

**Direction board (#222).** The local model, Gemini and ChatGPT hold a team meeting there by themselves: every 4 hours while the owner's PC is on (`board_every_hours`), after every 5 merged PRs (`board_every_merges`), when fewer than 15 jobs are queued (at most hourly), weekly on Sunday, or when the owner comments **Discuss: <topic>**. Each meeting opens with a review of the work in progress (what is running, stuck, sent back by the gate or merged, and how the board's own earlier proposals turned out), then each adviser proposes up to 3 directions with their case (problem, evidence, risk, rejected alternative), debates them for 2 rounds (reading the whole discussion, arguing for or against, revising or withdrawing its own), and votes 1 to 5. The meeting is posted live: opening, each round, decision. **Board memory:** every meeting sees what was merged in the last 3 weeks, all open work, and the fate of earlier board ideas (done, open, declined, or closed as a duplicate), and is told not to propose them again. Before an idea is adopted, a duplicate check compares it with that memory: a cheap word match first, then Gemini Flash Lite for close calls only. A duplicate is not adopted, and the decision post says what it repeats. Proposals with an average of 3.5+ and no score below 3 are adopted as `from-board` issues carrying the votes and the debate, up to 5 a meeting and only while fewer than 25 jobs wait. **A proposal may only name files that exist.** The advisers' context now carries the repository's full top-level listing and the app file's own section markers, and `invented_paths()` discards at adoption any proposal whose text names a path not tracked by git, saying so in the decision post. #1374 asked to create `src/workflows/templates/miniprep.js` and `test/workflows/reusability.test.js` in a single-file app with no `src/` tree. Those two paths were the only invented part of a genuine request from Patrick for cloning workflow stages, and a downstream agent, seeing them, rejected the whole feature request as a hallucinated prompt from an unrelated project. The idea was real; its write-up was not. Test: `tools/local-manager/test_board_paths.py`. **A name it puts in backticks that is not in the app is reported, not rejected**, because proposing a new function is fair: `unknown_idents()` lists any camelCase backticked name absent from the app file, in the decision post and in the issue body, so the worker knows the name is the board's rather than the code's. #1384 rested its whole premise on `drawZoomInset`, which does not exist (the function is `zoomCompose`), and the path check could not catch it. Every adopted idea goes straight to `queued`, so the work starts at once (with `board-approved` too when all three advisers scored it 4 or more, `board_go_score`). **No board change to the app merges without Patrick's OK (his choice); PRs that only touch tests or docs still merge automatically.** A PR for a `from-board` issue that changes the app goes through the Test suite, the gate and the AI lead review. Then, instead of merging, it gets `awaiting-owner` and a **Ready for your OK** comment. Patrick replies **OK** on the PR (the manager adds `merge-ok` and merges it) or **No** (the PR is closed and the issue gets `owner-declined`). The queue leader never merges a PR labelled `awaiting-owner`. The manager posts with the owner's token, so it reads only comments without its own signature as his. The owner can reply **No n** to drop an adopted one or **OK n** to add one, but nothing waits for him. **Relay route:** an adopted idea that not every adviser scored `board_go_score` or more (at most `board_relay_max`, 2, a round) is labelled `relay-from-board` instead of `queued` and becomes an offline relay request for Patrick (`docs/RELAY.md`); if it expires unanswered it goes to `queued`.

- **Claude** reviews PRs changing the app automatically and is called on any PR with `@claude`.
- Agents never push to another agent's branch: a revision goes on a new branch.
- Several PRs may change the HTML file at once (up to 8). A PR that conflicts with main is rebuilt on main by the local manager when its own diff still applies, and otherwise restarted by the gate.

## The queue leader (automatic routing and merging)

`.github/workflows/queue-leader.yml` is rule-based, with no AI. It ran Google Jules through its API until 2026-11-12; that half is gone and what remains is what the other workers depend on:

- **`queued`:** the unassigned work queue. The leader hands each issue to `for-antigravity`, which the Antigravity CLI, the Antigravity API route and the scheduled desktop session all serve. An issue carrying `ag-returned` is left alone, so it stays in the queue for Codex and the `agy` CLI on the PC and can never bounce between the two.
- **`from-patrick`:** issues the owner reports. `docs/GOALS.md` sets the order of everything else.
- **Pausing:** if the PC is off *and* the Antigravity API is paused, the leader leaves the jobs in the queue rather than routing work nobody can take.
- **Merging:** a PR that touches only `tests/`, `docs/`, `README.md` or issue templates, with a clean Test suite report, is merged automatically. An empty PR is never merged, and anything that changes the app or a workflow gets `needs-coordinator`.
- **Follow-ups:** "New checks failing" in a merged PR's test report, and "Ready-to-file issues" in a merged `docs/*audit*.md`, become issues labelled `needs-triage`. A person or the coordinator moves them to `queued` after checking scope and scientific impact.
- **Checks:** on a schedule, when an issue is labelled, and whenever a Test suite run finishes. It also starts the cloud manager, because GitHub rarely fires the schedule.
